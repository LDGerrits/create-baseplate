## Player data

`PlayerDataService` (`src/Features/PlayerData/Server/`) loads each player's saved data with Lapis (`ServerScriptService.ServerPackages.Lapis`) when they join, and saves it when they leave. Other services require it, read a player's data with `PlayerDataService.get(userId)` and change it with `PlayerDataService.update(userId, function(data) ... end)`, which saves what the function returns: Lapis freezes the data, so return a changed copy, `table.clone(data)`. To save a new field, add it to the `PlayerData` type and `DEFAULT` in `PlayerData.luau`, to `validate` in the service, and to a Lapis migration (`migrations` in `newCollection` there) that adds it to data saved before; Lapis rejects data `validate` doesn't accept, and the player can't load. Studio saves to a mock DataStore, forgotten when the server stops, and specs give the service their own (`PlayerDataService.spec.luau`). Lapis moves only while physics runs, which an Open Cloud execution session (`mise run test:engine` in CI) doesn't do, so specs that load data go in a `whileSimulating` block (a `describe` that skips there), as that spec's do.
