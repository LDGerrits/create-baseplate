# Baseplate

Baseplate creates Roblox games, in roblox-ts or Luau, set up for coding agents, the way create-t3-app creates web apps. The repo follows create-t3-app's layout.

## Parts

- `cli/`: `create-baseplate`, the CLI (`pnpm create baseplate`). `src/cli/index.ts` reads the flags and asks the questions; `src/helpers/` copy the template, name the project, install and commit; `src/installers/index.ts` lists the languages and each one's add-on questions, and applies the chosen ones.
- The language is the first question and a fork in the road: `typescript` (roblox-ts, the default) or `luau`. Each has its own template, `cli/template/<language>/`, with the tools that language's developers use (Sloptor, Flamework, ESLint and pnpm packages; or Wally, StyLua, Selene and luau-lsp), and its own add-on questions. Both hold to the same standard for agents: one check, the hooks, the skills, tests in ree, stories in rur. A change to one template's shared machinery (hooks, `scripts/`, skills, CI) usually belongs in the other too.
- `cli/template/<language>/base/`: the game every project of that language starts from. It is a complete project with its own `AGENTS.md`, mise tasks, hooks and skills, which ship to every game created from it. To work on it, work inside that folder: run its commands there and follow its `AGENTS.md`.
- `cli/template/<language>/extras/<question>/<choice>/`: one add-on choice: `addon.json` (its packages, npm's or Wally's, and what the main files start), `AGENTS.md` (its section in the game's `AGENTS.md`), `files/` (copied over the game) and, for a tool, `mise.toml` (its pin and tasks, merged into the game's). A manifest can also remove packages and files, replace an `AGENTS.md` section or a line, vary by the UI choice (`byUi`), and refuse another question's choice (`conflicts`). `--places multi` is code, not a manifest (`src/helpers/makeMultiPlace.ts`, and `makeMultiPlaceLuau.ts`): it runs after the add-ons and moves the game into a multi-place layout, each place a folder in `projects/`; the template's mise tasks run per place through `scripts/each-place.ts`. Develop one inside a game created by the CLI, where its check runs. `CONTRIBUTING.md` documents every manifest field. CI creates games from sets generated from each language's questions and the manifests' `conflicts` (`.github/scripts/generate-matrix.ts`): each choice alone, everything together, and every two choices together somewhere.
- `cli/src/sync/`: `create-baseplate sync`, run in a game, merges this version's agent files (`AGENTS.md`, skills, hooks, the agent tools' settings; the list is in `agentFiles.ts`) into the game's, three ways against `.baseplate/agent-files.json`, which the CLI writes when it creates the game. A game's `package.json` pins the version in `baseplate.version`, which Renovate updates; the template's `renovate-fixups.yml` workflow then runs the sync. A new kind of agent file joins that list.
- `www/`: the docs site, Astro with Starlight. Pages are Markdown in `www/src/content/docs/`, listed in `www/src/sidebar.ts`; each is also served as `/<page>.md`, `/llms.txt` lists them for agents and `/llms-full.txt` holds them all. The site's address is `SITE_URL` in `www/src/site.ts`. Write them from what the template actually does: its `AGENTS.md`, README, skills and mise tasks.

The build copies the template into `cli/dist/template`, only the files git tracks or would track. npm drops `.gitignore` files and symbolic links from packages, so the copy holds `_gitignore` and `_symlinks.json`, and the CLI restores them.

## Checking your work

- At the root, for the CLI and the docs site: `mise run check` (format, lint, build, type-check, test).
- In `cli/template/<language>/base`: its own `mise run check`, as its `AGENTS.md` says.
- To see what a user gets: `pnpm --filter create-baseplate build`, then `node cli/dist/index.js <folder> --json` (with `--language luau` for a Luau game), and `mise run check` in that folder.
- In Claude Code, a Stop hook (`.claude/hooks/check.ts`) runs the root `mise run check` when files changed and hands a failure back before the agent stops.
- The commit hook (`.githooks/pre-commit`) runs the root's `mise run ci` on every commit, and a template's check when a commit touches its `cli/template/<language>/base`. Turn it on in a new clone with `git config core.hooksPath .githooks`.

## Releases

A change to `create-baseplate` (the CLI, the template or an add-on) comes with a changeset: `pnpm changeset`, then pick the bump and say what changed for someone creating a game. On main, `.github/workflows/release.yml` keeps a "Version packages" pull request open with the next version and `cli/CHANGELOG.md`; merging it publishes to npm with provenance, once the repository variable `NPM_PUBLISH` is `true` and the workflow is a trusted publisher of `create-baseplate` on npmjs.com. The version PR's CI runs only when the repository's GitHub App opens it (secrets `BOT_APP_CLIENT_ID` and `BOT_APP_PRIVATE_KEY`, Contents and Pull requests: read and write); the mise lock workflow pushes as the same app. Renovate's updates carry no changeset; the next release takes them along.

## Updates

Renovate (`.github/renovate.json`) opens updates for every package, mise tool, GitHub Action and add-on pin (`addon.json`, and an add-on's `mise.toml`), at least two weeks after release, as pnpm requires; rbx-forge and Rogen come in at once. Wally packages (the Luau template's `wally.toml`, and Luau add-ons' `addon.json`) come in at once too, since Wally's registry gives no release dates for the wait to count from, and never merge without a person. CI creates a game with every option on each update, so an update merges only when all of them still pass. With the Open Cloud key and its place set (the secret `ROBLOX_OPEN_CLOUD_API_KEY`, the variables `ROBLOX_UNIVERSE_ID` and `ROBLOX_PLACE_ID`), CI also runs the specs of created games in a real Roblox server (the `engine` job), so an update that breaks only in the real engine fails too; only that job's last step gets the key. Without the variables the job shows as skipped, so an update can merge without it. rbx-forge, Rogen and Rojo never merge without a person: the first two skip the wait that would catch a hijacked release, and a Rojo update needs a check CI can't make, that rbx-forge supports its Studio plugin. The template's `mise.toml` is locked (`mise.lock`, with each tool's checksums), and so is a created game's. Renovate updates a tool's pin but not the lock, so `.github/workflows/mise-lock.yml` here and `renovate-fixups.yml` in the templates run `mise lock` on Renovate's branches and push it, and `wally install` for a Wally update, which rewrites `wally.lock`; with a GitHub App in the secrets `BOT_APP_CLIENT_ID` and `BOT_APP_PRIVATE_KEY`, that push starts CI again and the update can merge. mise's own version is pinned in every workflow's `jdx/mise-action` and in the template's `cloud-setup.sh`, with the SHA-256s it checks; Renovate bumps them together in one update, and `.github/scripts/check-mise-pins.ts` (in CI) fails until those SHA-256s match the new release, so a person updates them and merges. Keep a new add-on's pins in its `addon.json` (packages) or `mise.toml` (tools) so Renovate finds them, and a new tool exempt from the two-week rule in both pnpm's `minimumReleaseAgeExclude` and Renovate's rule.

## Writing

Write the template's files for the game's developers and agents, not for this repo: a created game has no `cli/`, and its name replaces `my-game`. Comments, commit messages and pull requests are read by someone who never saw the conversation.
